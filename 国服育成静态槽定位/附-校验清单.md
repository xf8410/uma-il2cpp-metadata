# 校验清单：探针上机前 / 上机后该查什么

这份清单的作用是——**别把「静态分析对了」误当成「运行时一定对」**。静态表是从解密后的 SO 反汇编推出来的，理论上等价，但游戏版本、加载顺序、泛型实例化都可能让实际布局有差异。

---

## 一、上机前的静态检查（不需要设备，现在就能做）

| # | 检查项 | 怎么查 | 期望 |
|---|---|---|---|
| 1 | 探针里的 59 个字段名和 metadata 逐字一致 | 对比 `data/work_single_mode_offsets.json` 的 `fields` 与 `uma_probe.js` 的 `FIELDS` | 59/59 全中，无拼写差异 |
| 2 | 探针里的 RVA 和 `methods_rva.tsv` 一致 | 查 `set_IsPlaying` / `get_IsPlaying` / `get_Character` / `Singleton.get_Instance` 四个地址 | 完全一致 |
| 3 | `STATIC_CONSTS` 恰好是那 2 个 | 检查常量列表 | `PLAY_TIMING_TYPE_NUM`、`LOG_INFO_MAX` |
| 4 | 5 个写入点 RVA 与 `CALLERS` 表一致 | 逐项对比 | 5/5 |
| 5 | 游戏版本 = 分析用的 dec.so 版本 | 查包名与构建号 | `com.bilibili.umamusu` / `2.0.5.11220.09221715` |

**第 5 项是最容易出问题的地方。** 游戏一更新，SO 重编译，所有 RVA 全变，字段偏移也可能变。上机前先确认版本，别拿旧版探针打新版游戏。

---

## 二、上机后的验证顺序

探针分 5 步跑，**每一步失败都有明确含义**，不要跳步。

### 第 1 步：找到 IL2CPP 模块

```
期望：打印出模块名和基址
失败含义：游戏把 IL2CPP 静态链接进了 libunity.so / libmain.so，
          或者用了自定义导出表，需要改模块探测逻辑
```

### 第 2 步：找到两个类

```
期望：Gallop.WorkDataManager ✓ / Gallop.WorkSingleModeData ✓
失败含义：类名被混淆了，或 image 遍历漏了某个程序集
```

`WorkSingleModeData` 在 `umamusume.dll` 里（image[71]，typeStart=6168，typeCount=25910）。

### 第 3 步：59 个字段偏移自校验 ★ 关键

```
期望输出：一致 59 / 59
```

这是整条链的**等价性证明**。用 `il2cpp_field_get_offset` 拿运行时真实偏移，和静态表逐项比。

如果出现差异：

| 现象 | 可能原因 | 怎么办 |
|---|---|---|
| 差异集中在某几个字段之后 | 静态表从某个位置起整体偏移 | 回去查 `parse_metadata_fixed.py` 的字段归属逻辑，重点看 image 边界 |
| 差异零星散布 | 游戏版本不同 | 确认版本，重新解 SO |
| 所有字段都差同一个常数 | 静态表把 static 字段算进实例了 | 检查 `STATIC_CONSTS` 是否漏了某个 |
| `class_get_field_from_name` 直接返回 null | 字段名被裁剪 | 查 metadata 是否被 strip 过 |

### 第 4 步：单例链取值

```
期望：static_fields[0] → 非空 WorkDataManager → +0x58 → 非空 WorkSingleModeData
```

反向校验：读 `WorkSingleModeData` 对象头（首 8 字节）应该是它的 `Il2CppClass*`。如果不是，说明 `+0x58` 取错了。

### 第 5 步：挂读写点

```
期望：进出育成界面时，0x3895FA0 被调用，值 1 → 0
```

如果 hook 挂上了但一直不触发：

- 检查是不是在**主菜单**状态下测的（那时候本来就不该触发）
- 进一次育成再退出来，看有没有 1 → 0 的跳变

---

## 三、探针跑通之后能确认什么

「一致 59 / 59」出来之后，以下结论才算**真正确认**，而不是静态推断：

- ✅ 61 字段表的每个偏移都可信，可以放心写进正式代码
- ✅ `+0x19` 确实只有那一个写入口（运行时验证 hook 计数 = 静态分析结论）
- ✅ 单例链 `0xB8 → [0] → 0x58` 在运行时成立
- ✅ `WorkDataManager + 0x58` 就是育成数据本体，不是别的
