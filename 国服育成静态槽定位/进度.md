## 2026-11-12 · 静态槽定位打通，`isPlaying` 读写点唯一性确认

### 目标

给「扫内存版黑板」找一个稳定锚点——不靠硬编码地址，靠游戏自己的单例对象链摸到育成数据。

### 做成的事

**1. 单例链闭合**

```
Il2CppClass(WorkDataManager) + 0xB8 → static_fields
static_fields[0]                     → WorkDataManager（Singleton<T>._instance, token 0x04017D08）
WorkDataManager + 0x58               → WorkSingleModeData（token 0x04004102）
```

四条独立证据：`Singleton<T>.get_Instance` @`0x14BD694`、`get_SingleMode` @`0x3BEF274`、`WorkDataManager..ctor` 里的 `str x20,[x19,#88]` @`0x3BEF8BC`、5 个写入点全部走 `ldr x0,[x0,#88]`。

**2. 61 字段偏移表**

`WorkSingleModeData`（idx=8972, token=0x02000AC2）61 个字段，token `0x04004661`–`0x0400469D` 严格连续无缺口。其中 2 个是 static const（`PLAY_TIMING_TYPE_NUM`、`LOG_INFO_MAX`），实例字段 59 个。

**3. `isPlaying` 读写点唯一性**

扫全部 320 个方法（abs_idx 67087–67406），`+0x19` 的访存只有两处：

| 方向 | 方法 | 地址 | 指令 |
|---|---|---|---|
| 写 | `set_IsPlaying` | `0x3895FA0` | `strb` |
| 读 | `get_IsPlaying` | `0x3895F48` | `ldrb` |

**4. 5 个写入点语义**

全库扫 `bl 0x3895FA0`，恰好 5 处：`StartSingleMode` / `GoSingleModeView` 写 1，`ClearPlayData` / `d__19` / `d__65` 写 0。

**5. 整表校验锚点**

`get_Character` @`0x3896290` = `ldr x0,[x0,#48]; ret`，`+0x30` 与 idx=5 `<Character>k__BackingField` 精确吻合。

### 踩的坑

**坑 1：只匹配 `[x0, #imm]` 会漏一半**

第一遍扫描只找 `ldr/str [x0, #imm]`，320 个方法只命中 28 个。原因是访问器普遍先 `mov x19, x0` 把 `this` 存起来，后面都用 `[x19, #imm]`。

修法：跟踪 `mov x19/x20/x21/x22, x0` 的搬运链，再匹配 `[xN, #imm]`。命中涨到 57/320、23 个不同偏移。

**坑 2：`get_Character` 同时命中 0x30 和 0x38**

完整 getter 里有前置 null check（读 `+0x30` 判空）再取真值（读 `+0x38`），两个偏移都被记下来。

修法：看**最简形态**。`get_Character` 只有 `ldr x0,[x0,#48]; ret` 两条，所以 `Character` = `+0x30`；`+0x38` 是 `_raceConditions`（idx=6）。

**坑 3：仓库里 `fields.tsv` 的 `type_index` 列是错的**

详见下面 2026-11-11 那条。

## 2026-11-11 · metadata 解析器缺陷修复 + SO 代码段全量解密

### 目标

前一步拿到的 `fields.tsv` 明显不对劲——`WorkSingleModeData` 的字段全是 `Short/Mile/Medium/Long`，一看就是别的类。要找出根因。

### 根因

`typeDefinition` 表在**同一程序集内不是按 token 排序**，而 `fields` 表**严格按 token 排序**。

旧解析器用「按 typeDefinitions 数组顺序累加 field_count」求 fieldStart。只要组内有一处乱序，后面所有字段归属整体偏移一位；跨 image 边界更必然断裂（每个程序集的 field token 都从 `0x04000001` 重新开始，全局不唯一）。

实测组内 type token **逆序对 4985 个**。这不是"可能有问题"，是必然出错。

### 修法

```
for each image (73 个程序集):
    idxs = [typeStart, typeStart + typeCount)
    idxs.sort(key = typeDef.token)      # 组内按 type token 重排
    for i in idxs:
        fieldStart[i] = 游标;  游标 += fieldCount[i]
        methodStart[i] = 游标M; 游标M += methodCount[i]
```

### 验证

| 指标 | 结果 |
|---|---|
| 字段总分配 | 254,055 = fields 表条目数（size/12） ✅ |
| 方法总分配 | 213,983 = methods 表条目数（size/32） ✅ |
| 组内 type token 逆序 | 0 ✅ |
| 跨 image 断裂 | 0 ✅ |

修复后 `WorkSingleModeData`(idx=8972) 读出 61 个字段，全是私有字段和自动属性 backing field，语义正常。

### 顺带发现：string 表不是标准 length-prefixed

这份 metadata 的 string 表是 **null-terminated**，不是标准 v27 的 length-prefixed。

判据：

```
image[0].nameIndex = 29 → STR_O + 29 = 1217573
该处字节 = 'm'（0x6D），其后 0x00 终止 → "mscorlib.dll"  ✓
若按 length-prefix：0x6D 当长度 109 → 读出一串拼接名  ✗
```

解析器已加编码自动探测（看 `image[0]` 名是否以 `.dll` 结尾且全可打印）。

### SO 代码段解密

`libil2cpp.so` 有 1,215 段 / 17.61 MiB（AX 段的 24.2%）是 **XOR 0x97** 密文，覆盖 49,143 个方法（23.7%）。

判据演进三个阶段，最终版「入口前 4 条指令合法，≥2 条即豁免超小方法」→ 49,129/49,143 = **99.972%** 可反汇编。真坏例仅 14 个（低 16 位全是 `0xefbc`，区间表 256 字节窗口边界噪声，占 0.0065%）。

## 2026-11-10 · 国服 metadata 解密还原

### 目标

拿到国服 `global-metadata.dat` 的可读版本。

### 双重加固

1. 头部 sanity / version 字段被改写
2. 每 64KB 块内 `+0x1000 ~ +0x4FFF`（16KB）整段 XOR 0x66，约 25% 字节被翻

### 还原脚本

```python
d = bytearray(open('global-metadata.dat','rb').read()); N = len(d)
for p in range(N // 4096 + 1):
    if p == 0 or (p % 16) in (1, 2, 3, 4):
        for i in range(p*4096, min(p*4096+4096, N)):
            d[i] ^= 0x66
d[0:4] = (0xFAB11BAF).to_bytes(4,'little')
d[4:8] = (27).to_bytes(4,'little')
```

### 结果

- magic `0xFAB11BAF`，version 27 → Unity **2020.3.49f1**
- 31 个段连续到文件尾 `0x01EC1464`，无空洞无截断
- typeDefinitions 32,080 / methods 213,983 / fields 254,055
- 已知损失：第 0 块 `0x1000~0x4FFF`（16KB）是另一套高强度加密（不是 0x66），对应 `stringLiteral` 第 512~2527 项约 2016 条字面量缺失。类型/方法/字段全量完好
